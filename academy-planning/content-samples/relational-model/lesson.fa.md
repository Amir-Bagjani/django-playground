# رابطه، سطر، ستون و دامنه

> **هدف:** در `DB-00-001` یاد گرفتیم یک سناریو را به موجودیت، ویژگی و نمونه داده تفکیک کنیم. اکنون همان‌ها را با نام دقیق ریاضی‌شان می‌شناسیم: **رابطه**، **سطر**، **ستون** و مهم‌تر از همه، **دامنه** — همان چیزی که تعیین می‌کند چه مقادیری اجازه دارند در یک ستون بنشینند.

## ۱. مسئله واقعی

یک جدول بدون تعریف «دامنه» فقط یک شبکه‌ی خالی است. اگر نگوییم قیمت نمی‌تواند منفی باشد یا وضعیت فقط یکی از چند مقدار مشخص است، هر برنامه‌ای می‌تواند داده‌ی بی‌معنا وارد کند. سؤال این درس: **مرزهای مجاز هر ستون کجاست؟**

## ۲. چهار نام دقیق

| اصطلاح رابطه‌ای | یعنی چه | معادل در جدول |
|---|---|---|
| **رابطه (Relation)** | یک مجموعه از نمونه‌های هم‌نوع با ساختار یکسان | جدول |
| **سطر / تاپل (Tuple)** | یک نمونه‌ی کامل با مقدار برای همه‌ی ستون‌ها | یک ردیف |
| **ستون / ویژگی (Attribute)** | یک خاصیت که برای هر نمونه مقدار می‌گیرد | یک ستون |
| **دامنه (Domain)** | مجموعه‌ی مقادیر مجاز یک ستون | نوع داده + قیدها |

نکته‌ی کلیدی: رابطه **نام** دارد (مثل `products`)، سطرها **هویت مستقل** ندارند تا وقتی یک کلید تعیین نکنیم، و ستون‌ها **نام و دامنه** دارند.

## ۳. دامنه: قلب این درس

دامنه تعیین می‌کند چه چیزی «مجاز» است. برای هر ستون یک دامنه داریم:

| ستون | دامنه‌ی مجاز | نمونه‌ی مجاز | نمونه‌ی نامعتبر |
|---|---|---|---|
| `name` | متن غیرخالی، حداکثر ۸۰ نویسه | `Printer` | (خالی) |
| `price` | عدد اعشاری نامنفی با دو رقم اعشار | `249.90` | `-5` |
| `stock` | عدد صحیح نامنفی | `0` | `-1` |
| `discontinued` | فقط `0` یا `1` | `1` | `2` |

دامنه می‌تواند ساده باشد (یک نوع داده) یا مرکب (نوع + قید مثل `>= 0`). هرچه دامنه دقیق‌تر تعریف شود، داده‌ی نامعتبر زودتر رد می‌شود.

## ۴. رابطه یک «مجموعه» است، نه یک لیست

در مدل رابطه‌ای، رابطه یک **مجموعه (set)** است. دو پیامد مهم:

- **ترتیب سطرها معنایی ندارد.** اگر می‌خواهی نتیجه مرتب باشد، باید صریح `ORDER BY` بنویسی (در `DB-02`).
- **سطر تکراری کاملاً یکسان بی‌معناست.** برای اینکه هر سطر هویت داشته باشد، از یک **کلید** استفاده می‌کنیم (در ادامه‌ی دوره: `DB-00-005`).

دو عدد مفید:

- **درجه (Degree):** تعداد ستون‌ها (اینجا ۴).
- **کاردینالیتی (Cardinality):** تعداد سطرها (که با هر درج تغییر می‌کند).

## ۵. نگاشت به SQL و Django

همان رابطه را در MySQL 8.4 می‌سازیم (مثال تشریحی، نه پاسخ تمرین‌ها):

```sql
CREATE TABLE products (
  id           INT NOT NULL AUTO_INCREMENT,
  name         VARCHAR(80) NOT NULL,
  price        DECIMAL(10,2) NOT NULL,
  stock        INT NOT NULL DEFAULT 0,
  discontinued TINYINT(1) NOT NULL DEFAULT 0,
  PRIMARY KEY (id),
  CONSTRAINT ck_price_nonneg CHECK (price >= 0),
  CONSTRAINT ck_stock_nonneg CHECK (stock >= 0)
);
```

توجه: در MySQL، نوع `TINYINT(1)` **دامنه را به ۰ و ۱ محدود نمی‌کند**؛ `(1)` فقط «عرض نمایش» است. برای اجبار واقعی مقدار بولی باید `CHECK (discontinued IN (0,1))` هم بنویسی (یا منطق را در سطح برنامه اعمال کنی). این تفاوت بین «نوع داده» و «دامنه» دقیقاً همان نکته‌ی این درس است.

در Django 6.1، یک مدل متناظر چنین است:

```python
from django.db import models

class Product(models.Model):
    name = models.CharField(max_length=80)
    price = models.DecimalField(max_digits=10, decimal_places=2)
    stock = models.IntegerField(default=0)
    discontinued = models.BooleanField(default=False)
```

نگاشت دقیق نیست و باید با دقت خوانده شود:

- هر فیلد Django یک ستون می‌سازد و **نوع فیلد** بخشی از دامنه را بیان می‌کند.
- `CharField(max_length=80)` هم در اعتبارسنجی ORM و هم به‌صورت ستون `VARCHAR(80)` در دیتابیس طول را محدود می‌کند؛ اما `IntegerField` هیچ قید بازه یا علامت (منفی/مثبت) در سطح دیتابیس نمی‌سازد. یعنی پوشش دامنه در ORM و دیتابیس **هم‌ارز نیست**: بعضی قیدها فقط در دیتابیس، بعضی فقط در ORM، و بعضی در هیچ‌کدام اعمال نمی‌شوند. جزئیات در `DB-01` و `DB-07`.
- ستون `id` را Django به‌طور پیش‌فرض به‌عنوان کلید اصلی خودکار اضافه می‌کند و نوع پیش‌فرض آن امروزه `BigAutoField` است (ستون `BIGINT`)، نه `INT`؛ پس با SQL دست‌نویس بالا نوع کلید دقیقاً یکی نیست.

> برای دیدن SQL واقعیِ تولیدشده‌ی یک Migration با دیتابیس زنده، در `DB-09` از `sqlmigrate` استفاده می‌کنیم.

## ۶. کلید: پیش‌درآمد

چون سطرها ترتیب و هویت ذاتی ندارند، برای اینکه بتوانیم به یک سطر خاص اشاره کنیم به **کلید** نیاز داریم. ساده‌ترین حالت، ستون `id` است که هر سطر را یکتا می‌کند. تعریف دقیق «کلید نامزد»، «کلید اصلی» و «کلید خارجی» در درس `DB-00-005` می‌آید.

## ۷. یادداشت مهندسی

دامنه را **پیش از** نوشتن کد تعیین کن. اگر دیر تعیین کنی، داده‌ی نامعتبر قبلاً وارد شده و بعداً باید پاک‌سازی (Backfill) کنی — کاری پرهزینه. دامنه را همان‌جا که قانون کسب‌وکار می‌گوید مستند کن، حتی اگر امروز بخواهی آن را فقط در سطح برنامه اعمال کنی.

## ۸. خطاهای رایج

**الف) تکیه بر ترتیب سطرها.** فرض‌کردن «سطر اول همان جدیدترین است» غلط است؛ بدون `ORDER BY` هیچ ترتیبی تضمین نمی‌شود.

**ب) دامنه‌ی مبهم.** نوشتن `price` به‌عنوان `FLOAT` برای پول، بعداً خطای گردکردن می‌سازد؛ `DECIMAL` انتخاب مالی است (`DB-01-005`).

**ج) یکی‌گرفتن اعتبارسنجی ORM و قید دیتابیس.** اگر قاعده فقط در Django باشد، نوشتن مستقیم SQL آن را دور می‌زند.

## ۹. تمرین‌ها

- **تمرین (Practice):** یک رابطه را با ستون‌ها، دامنه‌ها و یک کلید در Designer می‌سازی.
- **تمرین (Problem Solving):** برای یک رابطه‌ی داده‌شده، دامنه‌ی هر ستون، درجه و کاردینالیتی را تعیین می‌کنی و سطرهای نامعتبر را علامت می‌زنی.
- **چالش (Mastery):** یک رابطه‌ی نو با یک تصمیم واقعی (کلید طبیعی در برابر جانشین و مدیریت مقدار اختیاری) را مستقل طراحی می‌کنی و برای هر ستون دامنه و یک قید مشخص می‌کنی.

معیار قبولی هر تمرین زیر ویرایشگر است. توجه: تمرین‌های این درس در وضعیت فعلی موتور **خودکار نمره‌گذاری نمی‌شوند** و به بازبینی دستی نیاز دارند.

## مرور و گام بعد

خلاصه: یاد گرفتیم **رابطه**، **سطر (تاپل)**، **ستون (ویژگی)** و **دامنه** چه هستند؛ اینکه رابطه یک مجموعه است و ترتیب سطرها معنایی ندارد؛ و اینکه نگاشت SQL و Django در سطح دامنه هم‌ارز نیست.

گام بعد: در `DB-00-004` تفاوت **Schema** (ساختار) و **Instance** (داده‌ی جاری) را می‌بینیم و سپس در `DB-00-005` تعریف دقیق کلیدها می‌آید.
